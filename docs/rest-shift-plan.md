# Rest vertical-shift plan (option 3 — the shift travels with the music)

Let a user select a rest and nudge it up/down by whole staff-steps with the
arrow keys (↑ = +1, ↓ = −1), on top of the automatic multi-voice rest
placement. A composer's fine-positioning tool for voice clarity.

The graphical fix belongs to **that rest in the music**, so it **travels with the
content**: copy a passage and paste it elsewhere (a canon / out-of-sync effect)
and the shift comes along; a rebar that re-lays the bar keeps a fix you made by
hand. This is **option 3** — the durable design. (The earlier draft pinned the
shift to a fixed bar+beat and lost it on paste/rebar; that is superseded.)

Status: **PLANNED** (option-3 design 2026-06-27, reviewed against the codebase,
not started).

---

## 1. What this is (and is not)

- A rest's vertical position carries **no musical meaning** — a rest is
  pitchless, so where it sits vertically is purely an engraving/clarity choice.
  Moving it is therefore **geometry**, not content.
- It is a **shift**, measured in whole **staff-steps** (a notation unit), **not a
  pixel offset**. Staff-steps are resolution-independent, so this honors
  principle 3 (no pixels/layout in the model) the same way the slur overrides do
  by storing staff-spaces.
- It is **not** a side/direction flip. Flips (stem / tie / slur / articulation
  above↔below) are a finite categorical choice and stay on the content model.
  This is an open-ended "how far" magnitude → engraving-overrides compartment.
  See `DESIGN-PRINCIPLES.md` §3 and its "semantic flips stay on content" note.

So this is **client #5** of `score.engravingOverrides`, alongside `curveShape`,
`segmentCurveShape`, `endpointOffset`, `segmentEndpointOffset`.

## 2. The default stays

The automatic multi-voice placement is unchanged: `VexFlowRenderer.ts:402`
keeps `REST_LINE_SHIFT` and the per-voice `restShift` (V1 up, V2 down). The
per-rest override is a **delta added on top of** that base. With no override a
rest renders exactly as today.

(Whether the default magnitude should drop from 2 to 1 — the separate "too high"
finding — is **out of scope here**; this plan only adds the manual adjustment.)

## 3. Two coordinate forms: stored position, transported offset

The shift has to do two jobs, and they want two different keys:

1. **Render** wants to look the shift up cheaply while drawing a specific rest in
   a specific bar. → **Stored** in `score.engravingOverrides` keyed by the rest's
   **position address** (§3.1).
2. **Travel** (copy/paste, rebar) wants the shift expressed relative to the
   *music*, so it lands wherever the music lands. → **Transported** as a
   **region-relative offset** (§3.2).

The stored form is the source of truth; the transported form is a momentary
representation used only while content is being moved, then re-stored. This is
exactly how the codebase already moves beat-anchored things (clefs, dynamics)
through a rebar — see `captureBeatAnchors` / `restoreBeatAnchors`
(`ScoreModel.ts:1106,1129`). We add the rest-shift twin of that pair.

### 3.1 Stored form — position address

Rests are not durable objects: rest-fill erases and regenerates every rest in a
bar on any edit, minting a fresh `uuidv4()` (`ScoreModel.ts:211`, rebar relay
`:1441`). So the stored key cannot be a rest id. It is a **position address**:

```
{measureId}:v{voice}:b{num}/{den}
```

- **`measureId`, not `measureNumber`.** `insertMeasureAfter` / `removeMeasure`
  (`ScoreModel.ts:176-181, 238-243`) splice + renumber **in place** — the measure
  object and its `id` survive, only `m.number` / `slot.measure` change. A `number`
  key would silently re-point at a different bar on an insert-before (and could
  misapply to an unrelated rest there); `id` is stable across renumbering and
  across rebar (existing bars are cleared + re-materialised in place).
- The beat `Fraction` is reduced to lowest terms (`fracCreate` already reduces;
  the key builder reduces defensively) so `2/4` and `1/2` collapse to one key.
- `voice` is in the key, so V1's rest and V2's rest on the same beat are
  independent seats — the whole point, since the collisions being fixed only
  exist because voices share a beat.

Render and the keyboard mutator both derive this key from a rest's position. A
**plain same-bar edit** (add/delete a *note* elsewhere in the bar) regenerates
the rests with new ids but leaves the shifted rest on its beat → its position key
is unchanged → the shift re-attaches automatically, with no travel step needed.

### 3.2 Transported form — region-relative offset

When content is **moved** (rebar re-lays a region; paste overwrites a window),
rests are not relayed as themselves — `flattenRegion` **drops rests entirely**
(`rebar.ts:187`, "gap — regenerated by relay"), and `relayEvents` rest-fills
fresh rests for the new bar layout. So there is no event to ride on, and the
position key would point at a beat the rest may no longer occupy.

The shift therefore travels as a side-channel, captured **before** the move and
re-stored **after**, keyed by the rest's **absolute offset from the region/clip
start** (cumulative measure capacities + in-bar beat), plus voice and steps —
identical in spirit to how `captureBeatAnchors` snapshots a dynamic's absolute
offset:

```
{ voice, absBeat (offset from region start, quarter-beats), steps }
```

On restore, walk the new bars accumulating capacities, find which (measure, beat)
each offset now lands at, and **if a rest starts there**, write a fresh stored
override (§3.1) at that position. If no rest starts at the offset (the meter
change re-tiled the gap so nothing begins exactly there), the shift is **dropped**
— benign, see §4.

## 4. Behavior across operations (what the user asked about)

| Operation | What happens |
|---|---|
| Edit other notes in the same bar | Shift survives (stored position key unchanged, §3.1). |
| **Copy/paste, same meter** (the canon effect) | Shift **travels exactly**: the clip carries it at clip-relative offset; paste re-bases by the paste start; the regenerated rest at that offset is re-stamped. |
| **Rebar / meter change** | Shift travels **best-effort**: re-stamped onto whatever rest now *starts* at the same region-relative offset (so a quarter rest merged into a half rest at the same start keeps it); **dropped** only when the new tiling puts no rest start at that offset. |
| Insert / remove a measure | Survives (measure-`id` key, §3.1). |
| Rest's beat becomes a note (plain edit) | Stored entry stops being read (no rest there) — visually gone. Restoring a rest there later resurrects the prior shift (accepted, see below). |

**Identity rule:** a rest is matched by its **start offset within its voice**,
duration-agnostic. This is the most a pitchless, regenerated object can offer; it
makes same-meter paste exact and meter-change rebar graceful, and there is no
stable rest id to do better. A genuine duration merge/split that moves the start
is the only irreducible loss.

**Resurrection (accepted):** the stored form is position-keyed, so a `rest → note
→ rest` on a *plain* edit (no rebar/paste, so no capture/restore fires) returns
the previously authored shift rather than a fresh default. We accept this for
parity with the shipped `segmentCurveShape` decision ("accept resurrect-on-return,
no sweep") — it matches the engraving-overrides "operation-driven, not a sweep"
rule. No prune pass.

## 5. Scope & controls

- **Any rest**, not just multi-voice bars (a lone rest can be nudged too).
- **↑ = +1 step, ↓ = −1 step.** One step per press, **no coarse (Ctrl) mode** —
  rests don't travel far. (Revisit if needed.)

## 6. Implementation

### 6.1 Type — `types/music.ts`
```ts
export interface RestShiftOverride extends EngravingOverride {
  kind: 'restShift'
  /** Whole staff-steps, signed. Added on top of the default voice shift. +up. */
  steps: number
}
```
There is **no discriminated `EngravingOverride` union to extend** — `EngravingOverride`
(`music.ts:183`) is a base interface with `kind: string`, and each concrete kind
(`CurveShapeOverride`, …) is just an interface that `extends` it and is cast at read
sites (`as CurveShapeOverride`). So this is only a new interface plus the
`restShiftOverrideOf` cast-reader in §6.2 — nothing else to register.

Document on **both** this type **and** the `EngravingOverrides` compartment comment
(`music.ts:304-315`, today "Keyed by the *element id*") that this one client is
**position-keyed**, not id-keyed — a future reader must not assume every key resolves
to an element id. (Safe to mix: position keys contain `:`/`/` so they can never collide
with a uuid element id; nothing enumerates the table assuming id-keys; the only sweep is
the empty-check at `ScoreModel.ts:666`.)

### 6.2 Reader + key builder — `engravingOverrides.ts`
- `restShiftOverrideOf(score, posKey): RestShiftOverride | undefined` — mirror of
  `endpointOffsetOverrideOf`.
- `restPositionKey(measureId: string, voice: number, beat: Fraction): string` —
  canonical key builder (reduces the fraction). Pure, exported, unit-tested.

No prune helper (§4 accepts resurrection).

### 6.3 Stored mutator — `ScoreModel.ts`
`nudgeRestShift(posKey: string, delta: number): boolean` — upsert the override,
clear the entry (via `clearEngravingOverride`) when `steps` hits 0. **No undo here.**
ScoreModel mutators never own undo: `setSlurEndpointOffset` (`ScoreModel.ts:495`) just
upserts; the *facade* `MusicEngine.nudgeSlurEndpoint` (`:803`) calls `saveOnly(...)`.
The per-press snapshot therefore lives in the facade (§6.6), mirroring that pair.

### 6.4 Travel pair — `ScoreModel.ts` (the heart of option 3)
Model on `captureBeatAnchors` / `restoreBeatAnchors`:

- `captureRestShifts(regionMeasures): CapturedRestShift[]` — walk the region per
  voice; for each rest slot whose position key has a `restShift`, emit
  `{ voice, absBeat, steps }` (absolute offset from region start, pre-move
  capacities), then **clear** that stored override (it will be re-stamped, or
  intentionally dropped).
- `restoreRestShifts(regionNumbers, captured): void` — build the new bars'
  `{measure, start, cap}` ranges (same loop as `restoreBeatAnchors`); for each
  captured shift find the target measure, derive the local beat, and **only if a
  rest slot starts at that (beat, voice)** write the entry via the stored mutator at
  the new `restPositionKey(measure.id, voice, beat)`. Unlike `restoreBeatAnchors`
  (which unconditionally re-creates the clef/dynamic at the clamped beat), this needs
  the explicit slot check — there is no ready-made accessor, so read the
  post-`materializeRegion` measure directly:
  `measure.slots.find(s => s.type === 'rest' && (s.voice ?? 0) === voice && fracCompare(s.beat, beat) === 0)`.
  No match → the shift is dropped (§4, benign).

Wire both into the two content-moving pipelines right beside the existing
capture/restore calls:
- `rebarRegion` (`ScoreModel.ts:~901-970`): capture before flatten, restore after
  `materializeRegion`.
- `pasteEvents` (`ScoreModel.ts:988-1075`): restore from the **clip's** shifts,
  re-based by `pasteStart`, after `materializeRegion`.

### 6.5 Clipboard carries the shift — `clipboard.ts` + paste path
- `ClipboardVoice` (`clipboard.ts:21`) gains
  `restShifts?: Array<{ offset: Fraction; steps: number }>` — offsets relative to the
  **selection start**, the same basis as its `events` (which are re-based by `spanStart`).
- `buildClipboardFromSelection` (`clipboard.ts:98`, the copy builder — note it takes a
  plain `score: Score`, **not** a `ScoreModel`): for each selected voice, scan the
  selection window for rests carrying a `restShift` and record `{ offset, steps }`.
  Read the override straight off the value with `restShiftOverrideOf(score, key)` (the
  reader takes a `Score`, like `engravingOverridesOf`). This is in addition to the note
  `events`; a selected *rest* with a shift must copy even though it produces no note event.
- `pasteEvents` gains a `clipRestShifts: { voice; restShifts }[]` argument; after
  materialise it calls `restoreRestShifts` with each `offset` mapped to
  `pasteStart + offset`. `MusicEngine.paste` / `ClipboardController` thread the new
  payload section through (it is optional → older clips/no-rest clips are a no-op).

### 6.6 Facade — `MusicEngine.ts`
`nudgeRestShift(restId, delta)` — resolve the selected rest → its measure (look up
by the note's `.measure`, read that measure's `id`), voice, beat →
`restPositionKey` → model mutator, then `saveOnly('Nudge rest')` on success (the
per-press undo snapshot lives here, exactly like `nudgeSlurEndpoint` at `:803`).
Public arg stays the selected rest id; translate inside.

### 6.7 Keyboard — `useShortcuts.ts`
In `pitchUp` / `pitchDown`: if the selection is a **single rest**, call
`nudgeRestShift(+1 / −1)` and consume; else fall through. Slot it into the
existing chain *after* the armed-slur-point check (`useShortcuts.ts:240-241`).
Safe — `adjustPitch` (`SelectionController.ts:439`) skips rests in its loop and
reports nothing moved for a lone rest, so no existing behavior is taken.

### 6.8 Render — `VexFlowRenderer.ts` + `NoteBuilder.ts`
At `VexFlowRenderer.ts:402` keep the per-voice base `restShift`. Widen
`createStaveNotesFromSlots`'s `restLineShift` from `number` to
`number | ((slot: ChordRest) => number)` — mirroring the `clefForBeat:
((beat) => Clef) | Clef` overload right above it. The renderer passes a resolver
that builds each rest slot's position key (it holds `measure.id`, `slot.voice`,
`slot.beat`), looks up `restShiftOverrideOf`, and returns `base + steps`.
NoteBuilder calls it where it reads `restLineShift` today (`setKeyLine`,
`NoteBuilder.ts:118`, and the measure-rest branch `:105`) — stays score-agnostic;
the score lookup lives in the renderer's resolver closure.

## 7. Tests (co-located, vitest)
- `restPositionKey` canonicalization (`2/4` === `1/2`; voice + measure id in key).
- nudge up/down accumulates; returning to 0 clears the entry.
- plain same-bar edit of another beat → shift survives (position-key win).
- insert a measure before the shifted rest → shift survives (measure-`id` win).
- **copy a shifted rest, paste at a different beat, same meter → shift travels to
  the new position** (the canon effect — the core option-3 test).
- **rebar (meter change) keeps the shift when a rest still starts at the offset;
  drops it when the new tiling has no rest start there.**
- rest's beat becomes a note on a plain edit → not drawn; restoring a rest there
  resurrects it (§4 accepted).
- per-voice independence (V1 up, V2 down on the same beat, no interference).
- render: rest renders at base ± override steps.

## 9. What option 3 does NOT solve
- A rebar that **merges/splits a rest's duration** so its start offset moves: the
  identity (start offset within voice) no longer matches → shift dropped. This is
  irreducible without a real rest id, and is rare/benign.
- Cross-meter paste (clip meter ≠ target meter) re-tiles like a rebar → best-effort
  by the same offset rule.

## 10. Deferred render polish (after the plan ships)
- **Ledger lines for shifted rests.** A half rest hangs from a staff line and a whole
  rest sits under one; their vertical position is read against those lines. When a rest is
  shifted far enough to sit **above or below the staff**, VexFlow draws **no ledger lines
  for rests**, so the eye loses the reference and a quarter/half/whole rest's exact
  position becomes ambiguous. This is a pure rendering concern (the stored shift is already
  correct); fixing it means drawing ledger line(s) through a rest that lands outside the
  staff, like a notehead would get. Deferred — NOT a blocker for the storage/travel logic
  above. Revisit once the core feature is in.
